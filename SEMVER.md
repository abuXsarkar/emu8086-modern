# Versioning policy

`emu8086-modern` follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)
starting from `1.0.0`. This document spells out what counts as a
breaking change for each component, because the answer is not the
same across the workspace.

## The user-facing surfaces

| Surface | What versions track |
|---|---|
| Web IDE (`@emu8086/web`) | URL behavior, `localStorage` keys, share-link fragment format |
| CLI (`emu8086`) | Subcommand names, flag names, exit codes, JSON / JUnit XML schemas, YAML grader spec keys |
| Assembler (`@emu8086/assembler` Rust crate) | Mnemonics it accepts, directives it understands, byte output for a given source |
| Emulator core (`@emu8086/core` Rust crate) | Public Rust API; observable behavior of each instruction (flag updates, memory writes, port writes, exit codes) |
| Wasm API (`@emu8086/wasm-api`) | Exported function names + signatures the IDE calls |
| Plugin SDK (`@emu8086/plugin-sdk`) | `DevicePlugin` / `DevicePluginProps` types; `registerDevicePlugin` signature |
| Classroom protocol (`@emu8086/classroom-protocol`) | `ClientMsg` / `ServerMsg` shapes, `PROTOCOL_VERSION` constant |
| Desktop shell (`@emu8086/desktop` / Tauri bundle) | Bundle identifier, native deep-link scheme |

## Breaking changes (MAJOR bump required)

Any of these in a stable release is a breaking change:

### Web IDE

- Renaming or removing a `localStorage` key the IDE reads (`emu8086.source`, `emu8086.editor-theme`, etc.).
- Changing the share-link fragment format such that an old link decodes to a different program — or fails to decode at all.
- Removing a UI surface students were trained on (the Run/Step/Back triple, the device gallery, the debugger).

### CLI

- Renaming or removing a subcommand or flag.
- Changing an exit-code mapping (today: `0` = success, `1` = assemble error, `2` = runtime error, `3` = grader failure).
- Changing the JSON schema of `trace` or the JUnit XML emitted by `grade --junit` such that an existing CI consumer would mis-parse.
- Changing the YAML grader spec format such that an existing spec stops loading.

### Assembler / core

- Rejecting a program that used to assemble cleanly (unless the old behavior was undocumented and clearly wrong — these go in the changelog with a migration note).
- Changing the byte output for a given source for a documented mnemonic.
- Changing the observable behavior of an instruction (flag updates, side effects).
- Removing a documented INT subfunction.

### Plugin SDK / Classroom protocol

- Renaming or removing a field from `DevicePlugin` / `DevicePluginProps`.
- Changing the meaning of an existing `ClientMsg` / `ServerMsg` discriminant.
- Anything that requires the `PROTOCOL_VERSION` to bump.

## Non-breaking (MINOR or PATCH)

- Adding a new instruction, INT subfunction, directive, or assembler form.
- Adding a new CLI subcommand, flag, or output mode.
- Adding a new field to a JSON / YAML / protocol type **as long as old consumers ignore it without error**.
- Adding new translations, themes, examples, or tutorials.
- Adding a new built-in device or shipping a new bundled plugin.
- Fixing a bug whose previous behavior was clearly wrong (e.g. an `ADD` that miscomputed `OF` for one corner case).
- Any internal refactor that doesn't change the surfaces above.

## What we will deliberately *not* break

- **Course material that compiles today.** If a printed lab manual's program assembles + runs against `1.0.0`, it will assemble + run against every `1.x` release. This is the strongest stability promise we make; it's the whole point of the project.
- **Existing share-links.** A link generated by `1.0.0` will keep opening correctly in every `1.x`. We may add new fragment keys (`#prompt=…`, etc.); we won't change `#code=` semantics.
- **YAML grader specs** written against `1.0.0`. New optional keys are fine; renames + removals require a major bump.

## Compatibility windows

We support **the latest minor of the latest major** with security fixes. Older minors of the latest major receive critical-only patches at our discretion. Older majors are end-of-life.

If you need a guaranteed support window for an institute deployment, pin to a `1.x` release and self-host. The MIT license means you can keep running any version forever.

## Pre-1.0 (now)

Until `1.0.0` ships:

- Anything labelled `0.x` in `package.json` / `Cargo.toml` is considered unstable.
- We try not to break things gratuitously, but no SemVer guarantees apply yet.
- The CHANGELOG's `[Unreleased]` section is the source of truth for what's new on `main`.
